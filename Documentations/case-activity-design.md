# Case Activity design

Add a dedicated Case Activity log to the case list and the 2D and 3D case menus. The log belongs to one case and shows when each action happened, who performed it, which users were involved where applicable, and the outcome. Version History keeps its own menu entry, data source, and behavior. Case Activity uses its own table and API and starts recording at rollout.

Use separate labels for the actor and affected users. For example, show “Alex assigned Priya to the case” or “Alex transferred ownership from Morgan to Priya.” For a design save or case open, show the actor alone. A former collaborator can still appear on past entries. Their current access is checked independently of their historical involvement.

The first release covers the web app, including the public shared viewer. Record deliberate case operations, including opens, saves, messages, exports, and unsaved design edits. Record both successful and failed actions. Pointer motion, camera movement, background polling, preload requests, and automatic retries do not generate separate activity rows. Record shared-view activity as anonymous, with no attribution to the link owner. Desktop and Unity instrumentation are outside this release.

## Capture points

The existing Graphify report identifies the case management and 2D annotation entry points. The table maps those flows and the viewer to the routes and functions checked in source.

| Action | Current path | Capture point |
| --- | --- | --- |
| Create, rename, delete, restore, duplicate | `createCase.js`, `caseManagement.js` and the API `/case` routes | Case model transaction. Audit the creator even if an administrator assigns someone else as owner. For duplication, write one source event and one destination event with the same operation ID. Apply case access checks before displaying a link to the other case. |
| Change status, assignee, due date, instructions, tooth shade | `caseManagement.js` and `caseNote.js` write `/additionalcasedetails`. Tooth shade also has its own route. | Compare the prior and saved state in the transaction. Status lives in `additional_case_details.new_status`. A status field carried forward by another edit does not generate a status event. Record changed field names and allowlisted status codes. |
| Assign or remove a role, transfer ownership, change a case flag | `caseManagement.js`, `caseRoles.js`, `/role`, `/role/owner`, `/role/delete`, `/usercasestatus/setflagged` | Role or flag write. Store stable target IDs and role codes as needed. Treat automatic read-state updates as background traffic. |
| Edit or save 2D or 3D work, update clinical data, lock a survey angle, update noticeboard | `2DAnnotation.js`, `jawStructApi.js`, `clinicalInfo.js`, `noticeboard.js`, and the web 3D viewer | Report discrete local edits at the command boundary, including add, move, remove, undo and redo where available. Emit one move per completed gesture. Keep these entries labeled as unsaved edits even after a separate save event. Audit durable writes for jaw structures, clinical and jaw data, survey lock, and noticeboard content. Group multiple jaw saves by operation and record partial saves at the resource level until there is a transactional batch endpoint. |
| Upload, replace or remove case files | `createCase.js`, `/referenceimages`, `/fileattachments`, STL and slot routes | Audit the durable file write or delete. Capture the asset type or slot and internal record ID. |

Approval uses workflow status updates and can send notifications. | Derive note author from authenticated identity. Add a dedicated authenticated note write and migrate the browser to it. Inventory and migrate legacy callers before closing the old write path. Capture the approval decision at the status write. | Create, replace or revoke a share link | `shared/caseLinks.js` and `/case/share/replace`, `/case/share/revoke` | Share-link write after owner or admin authorization. Record lifecycle events without storing the share URL, token, or hash. |

Record case opened after the case view loads. Record export initiated when the browser is ready to hand off the file. Server download routes can record bytes served, where applicable. Neither signal confirms a file was saved to disk. |

## API and persistence

- Use the existing request envelope for `POST /api/smartrpd/case/activity/get`. Accept a case ID, an optional opaque `before` cursor bound to that case, and a limit defaulting to 50 with a maximum of 100. Return `{ events, nextCursor }` ordered by descending event ID. Serialize BIGINT IDs as decimal strings. Current owners, co-owners, case users, and administrators can see the full log. Check current permissions on every page, and use existing recovery permissions for soft-deleted cases. Reject guest and share principals explicitly because the existing case-read guard can admit them.
- For mutations, derive actor UUID and target case from verified authentication and the row being written. Do not copy actor, outcome, or timestamp from the browser. Append the activity row in the same database transaction as the change using a dedicated checked-out connection. The existing DB wrapper exposes transaction methods on one shared connection, so do not extend that pattern to new concurrent audited operations. If the audit insert fails, roll back the case change and return the operation error.
- Use server UTC time with microsecond precision. Store action codes and minimal per-action metadata, such as changed field names, jaw, or affected internal record IDs. For assignment, access changes, and ownership transfers, include affected user UUIDs and their relationship to the action in the existing JSON details field. Derive these from the records changed by the server. Omit clinical values, patient details, names of files, message bodies, model data, and credentials. Resolve actor and affected-user display labels for authorized readers and fall back to a generic label if an account is unavailable.
- For browser-only actions, add `POST /api/smartrpd/case/activity/signal` with a fixed allowlist, a case access check, and per-user rate limits. Derive identity and time server-side. Mark these entries as browser-reported. Reuse a UUID per intent and check ownership of the operation ID on a duplicate. Use a bounded in-memory queue to retry transient delivery failures. Browser signals can still be lost when a page closes and can be fabricated by an authorized client.
- For anonymous shared-view activity, validate the share credential server-side and derive the case from it. Accept only shared-view actions such as opens and export attempts. Apply rate limits per share credential and store a null actor UUID. Invalid, expired, and cross-case share attempts belong in operational security logs because the case or principal cannot be trusted. A share principal can submit those limited signals and cannot read the activity log.
- Record failures after verifying actor and case scope. Write a terminal failure event after rollback with an allowlisted reason such as validation failure or storage failure. For browser-only actions, report a bounded failure code from the UI. Treat a network timeout with no server result as unknown. Use distinct event keys for attempt outcomes and committed operations so a lost response or a retry cannot conceal a committed event. Exclude unauthenticated and cross-case failures from the case timeline. When the database is unavailable, record a minimal operational error because the case activity table may also be unreachable.
- Enable the audit timeline and browser signals for the web flow first. For routes shared with Unity, establish how the server can identify a web operation before enabling web-only writes. Keep the audit actor tied to verified credentials. A client-supplied source label can describe where a signal came from and cannot prove which client called a route.
- Use the unique index to prevent duplicate audit rows per case, operation and action. For workflows with multiple writes of the same kind, give each durable sub-operation its own ID and carry a common group ID in allowlisted metadata. Deduplicating the event does not make the mutation safe to retry. If mutation retry is supported, atomically claim the operation before the first side effect and validate that replays have the same actor and request. Keep existing write routes callable by desktop clients that do not send an operation ID.
- Grant the API audit-table SELECT and INSERT privileges only, using a separate migration account for DDL. Keep activity rows across soft deletion and avoid cascading foreign keys. Decide retention and hard-purge handling before production rollout.

## Implementation and acceptance

1. Run the accompanying Workbench SQL in a test schema. Verify the case key can be represented as a positive BIGINT, the table uses InnoDB, and timeline queries use the case index. Confirm audited business tables also use InnoDB before relying on rollback.
2. Deliver the first vertical slice with case rename, timeline reads, and the Case Activity UI. Verify two cases cannot read each other's records, a share link cannot query activity, revoked access takes effect between pages, and concurrent inserts do not duplicate rows on page traversal.
3. Add lifecycle, status and role operations. Test rollback on an audit insert failure, repeated no-op status writes, admin acting on behalf of an owner, both sides of duplication, and continued access to activity after soft-delete through authorized recovery views. Check that ownership transfers identify the actor, previous owner, and new owner, and that removing a user preserves their earlier entries while revoking their access to the log.
4. Add clinical and design saves, asset and noticeboard writes, authenticated chat, and share management. Run the web flows and check compatibility of shared routes with existing desktop requests. Verify partial jaw saves display the actual completed parts, chat author spoofing is rejected, and no sensitive payloads appear in rows or logs.
5. Add case opens, local design commands, exports, failed actions, and anonymous share signals. Verify that an unsaved edit still appears if the user leaves without saving, a failed save remains distinct from a committed save, and a public share signal can only be attributed to the credential's case. Test duplicate delivery, expired credentials, and exclusion of prefetches. Check every user-facing case command against the event inventory before enabling it in production.

See [case-activity.sql](case-activity.sql) for the proposed migration. Run it against the test database before enabling any API writers.

## Implementation status

The current changes add the timeline, the authenticated read and signal routes, and audited web writes for rename, soft-delete, restore, ownership transfer, case status, due date, instructions, chat, survey-angle saves, and per-jaw 2D design saves. Survey entries record the previous and saved direction vectors. Each 2D save identifies the jaw and whether the design data was unchanged. Browser reports cover case opens, supported exports, local 2D history changes and 3D polyline edits, undo and redo, and loading or reloading a proposed 2D design. These reports identify the browser as their source.

Run the SQL in a test schema and deploy the API before deploying the web changes. Verify the audited business tables use InnoDB and test the audit permissions with the API account. The web chat, survey-angle save, and 2D save paths require the new API routes. Audit coverage for the remaining rows in the capture-point inventory is pending, including case creation and duplication, general role and share management, file and clinical writes, and other design writes.
